## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Абатуров Никита |
| Вариант (запрос) | (Q3) |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | sf1 достаточно для демонстрации работы ETL и бенчмарков на локальной машине, не перегружая ресурсы Docker. Также позволяет быстро проверить логику без долгих ожиданий. |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище | Стандарт де-факто для локальных S3. Позволяет эмулировать облако без затрат |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Надежная реляционная БД для хранения каталога таблиц Iceberg |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Обеспечивает управление таблицами Iceberg |
| Trino | SQL-движок | Быстрый распределенный SQL-движок, нативно поддерживающий Iceberg и S3 |
| Metabase | BI-инструмент | Простой способ визуализировать Gold-слой без написания кода |


### Скрипты, которыми поднимал стек

```bash
# Контейнер с Trino (SQL-движок)
docker run -d --name trino -p 8080:8080 trinodb/trino

# Контейнер с Lakekeeper (REST Catalog)
docker run -d --name lakekeeper -p 8181:8181 lakekeeper/lakekeeper

# Контейнер с PostgreSQL (метаданные Lakekeeper)
docker run -d --name lakehouse-pg -p 5432:5432 postgres:14

# Контейнер с MinIO (S3-хранилище)
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 minio/minio server /data --console-address ":9001"
```

## 3. Разбор запроса — какие данные нужны

Запрос Q3 требует соединения трех таблиц.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| customer | custkey, mktsegment | Фильтр по BUILDING, join с orders |
| orders | orderkey, custkey, orderdate, shippriority | Фильтр по датам, join с lineitem. |
| lineitem | orderkey, extendedprice, discount, shipdate | Расчет выручки (revenue), join с orders. |

## 4. Медальон — решения по каждому слою

Как заполнять:
- **Строк** — `SELECT count(*) FROM таблица`;
- **Вес, МБ** — размер файлов таблицы в MinIO (консоль → бакет → объекты) или `SHOW STATS`;
- **Формат** — `PARQUET` / `ORC`;
- **Сжатие** — `NONE` / `SNAPPY` / `GZIP` / `ZSTD`;
- **Партиционирование** — по какой колонке (или «нет»);
- **Обоснование** — почему выбрал именно такой формат + сжатие + партиционирование для этого слоя и твоего объёма данных.

## 5. Тесты производительности


| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 12 с | 147,4 МБ | GZIP показал минимальное время и чуть меньший размер в данном тесте. Однако разница с ZSTD в пределах погрешности. |
| ZSTD | 12 с | 147,5 МБ | ZSTD обычно является современным стандартом для аналитики (лучше сжимает и быстрее распаковывает), но в текущей конфигурации Trino свойство сжатия не применилось, поэтому результаты идентичны. |


## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычные БД (PostgreSQL) не тянут петабайты данных и не умеют хранить сырые данные дешево. Lakehouse (Iceberg) позволяет хранить структурированные и сырые данные в одном месте (S3), обеспечивая ACID-транзакции и версионность (time travel). |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Если мы добавим колонку l_tax в silver.lineitem, Iceberg обновит метаданные. Старые файлы останутся нетронутыми, новые записи будут иметь новую колонку. Trino увидит изменения автоматически. |
| Пример скрипта восстановления данных из снапшота (time travel) | SELECT * FROM lakekeeper.silver.orders FOR VERSION AS OF 'snapshot_id'; — позволяет посмотреть данные на момент времени. |

## 7. Выводы

В ходе работы я развернул локальный Lakehouse на базе MinIO, Lakekeeper и Trino и на практике реализовал медальон-архитектуру (Bronze → Silver → Gold). Я понял, что медальон позволяет разделить ответственность: Bronze хранит сырые данные «как есть», Silver — очищенные и нормализованные (с переименованными колонками и фильтрацией), а Gold — готовые агрегаты для бизнес-аналитики. Использование формата **Parquet** оказалось оптимальным выбором для всех слоев, так как он колоночный и эффективен для аналитических запросов, а партиционирование `silver.orders` по году (`order_year`) значительно ускоряет фильтрацию по датам. По поводу сжатия: несмотря на то, что сравнение GZIP и ZSTD в текущей версии Trino не дало разницы (свойство `compression_level` не поддерживается), я понял, что для production лучше выбирать **ZSTD** — он обеспечивает лучшее соотношение степени сжатия и скорости распаковки. Мой выбор Lakehouse на Iceberg лучше традиционного хранилища (например, Hive) тем, что даёт ACID-транзакции, версионность (time travel) и schema evolution без перезаписи данных.
